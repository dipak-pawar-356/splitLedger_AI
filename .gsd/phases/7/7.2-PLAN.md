# Plan 7.2: Cryptographic Engine & Refresh Token Rotation Core

## Objective
Build the financial-grade cryptographic token service and refresh token rotation engine in `src/lib/security/token-service.ts`. Deliver signed, short-lived JWT access tokens (15 minutes), 256-bit entropy opaque refresh tokens stored only as SHA-256 hashes, constant-time validation, and automated token rotation with reuse attack detection and session lineage revocation.

<task type="auto">
  <name>Build High-Entropy Cryptographic Token Service</name>
  <files>
    src/lib/security/token-service.ts
  </files>
  <action>
    Create `src/lib/security/token-service.ts` using Node.js built-in `crypto` module (zero external npm bloat, edge/server compatible, highest performance):
    1. Implement JWT creation & verification with HMAC-SHA256:
       - Access Token Lifetime: 15 minutes (900s).
       - Header: `{"alg":"HS256","typ":"JWT"}`.
       - Payload: `sub` (user publicId), `uid` (user id), `sid` (session publicId), `did` (device publicId), `ver` (token version), `role`, `iat`, `exp`, `iss: "splitledger-ai"`, `aud: "splitledger-api"`.
       - Cryptographic signature generation and constant-time signature verification using `crypto.timingSafeEqual`.
    2. Implement Opaque Refresh Token Generator:
       - 256-bit cryptographically secure pseudo-random bytes (`crypto.randomBytes(32).toString('base64url')`).
       - Hash generator: `hashToken(rawToken: string): string` using SHA-256.
       - Never write raw refresh tokens to database or logs.
    3. Implement Cookie Utility:
       - Set `sl_access_token` and `sl_refresh_token` with `httpOnly: true`, `secure: process.env.NODE_ENV === "production"`, `sameSite: "lax"`, `path: "/"`.

    AVOID: Base64 decoding without cryptographic signature checks.
    AVOID: Storing refresh tokens in plain text in database or localStorage.
    USE: Constant-time comparison (`crypto.timingSafeEqual`) to prevent timing side-channel attacks.
  </action>
  <verify>
    npx tsc --noEmit
  </verify>
  <done>
    `token-service.ts` correctly creates, signs, verifies, and hashes tokens with constant-time equality and strong typing.
  </done>
</task>

<task type="auto">
  <name>Implement Atomic Refresh Token Rotation & Reuse Detection</name>
  <files>
    src/lib/security/token-service.ts
    src/actions/auth-session.ts
  </files>
  <action>
    Implement atomic Refresh Token Rotation with reuse detection in `src/actions/auth-session.ts` and `src/lib/security/token-service.ts`:
    1. Function `rotateRefreshToken(rawRefreshToken: string, clientContext: ClientContext)`:
       - Hash the incoming `rawRefreshToken` with SHA-256.
       - Query active session matching `refreshTokenHash = hashedIncomingToken`.
       - **REUSE ATTACK DETECTION**: If token is not found or points to an already revoked/expired session:
         - Identify if there is a session where this token was previously used (or find matching session by ID/cookie).
         - If reuse detected: IMMEDIATELY revoke all active sessions for that session lineage (`status = 'revoked'`, `revocationReason = 'token_reuse_detected'`).
         - Record high-severity security audit event (`type: "token_reuse_detected"`, `severity: "critical"`).
         - Return an authentication error rejecting the rotation.
       - **SUCCESSFUL ROTATION**:
         - Verify session is active (`status === 'active'`) and not expired (`now < expiresAt` and `now < idleExpiresAt`).
         - Generate a brand-new raw Refresh Token and new Access Token.
         - Atomically update session in database: update `refreshTokenHash = newHashedToken`, `lastActiveAt = NOW()`, `updatedAt = NOW()`.
         - Set new HttpOnly cookies on the response.
         - Return the new session state and access token.
  </action>
  <verify>
    npx tsc --noEmit
  </verify>
  <done>
    Token rotation generates new tokens upon each refresh, invalidates the previous refresh token, and detects reuse attempts by revoking the entire session lineage.
  </done>
</task>
